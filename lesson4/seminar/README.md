## [4. Лимит мест](tasks/Task04.kt)

Прочитай обязательный лимит мест. Убери пробелы по краям.
Если вход равен null или строка пуста после обрезки, вызови готовую missingCapacity().
Разбери число через toInt(). Поймай NumberFormatException и брось
EventConfigException, передав исходное исключение вторым аргументом (cause).

Примеры: " 5 " → 5, null → EventConfigException, "abc" → EventConfigException с cause.
Вопрос: почему missingCapacity() возвращает Nothing, а не Unit?

### 4б. Что произойдёт в `finally`?
Разбери этот код после того, как решишь основную задачу:

```kotlin
fun checkedCapacity(raw: String?, onFinish: () -> Unit): Int {
    try {
        return readCapacity(raw)
    } finally {
        onFinish() // Отмечает завершение проверки. Само действие не бросает исключений.
        return 0
    }
}
```

1. Не запуская код, предскажи результат для "25" и "abc". Дойдёт ли ошибка до вызывающего кода?
2. Исправь одну строку: для "25" должно вернуться 25, для "abc" должно выйти EventConfigException
   с исходной NumberFormatException в cause. В обоих случаях onFinish() должен вызваться ровно один раз.

## [5. Статус регистрации](tasks/Task05.kt)

Реши, можно ли зарегистрировать участника. requested — запрошенное число мест
после разбора (положительный Int или null), remaining — сколько мест осталось (0 или больше).
Верни ровно одну из строк: "Неверное количество мест", если requested == null;

Примеры: (null, 3) → "Неверное количество мест", (4, 3) → "Мест не хватает",

Функция только возвращает статус. Места списывать не надо.

## [7. Черновик заявки · 20–25 минут](tasks/Task07.kt)

Маша начала заполнять заявку и нажала «Отправить» без email. Она должна иметь возможность исправить тот же черновик. Но уже отправленную заявку менять нельзя.

Допиши `RegistrationDraft`. Каждый экземпляр хранит свои имя, email и признак отправки. В начале оба поля пусты, черновик не отправлен.

- `editName` и `editEmail` запоминают последний ввод, даже если это `null` или пока некорректная строка. Во время редактирования не проверяй формат.
- `submit()` получает имя через `displayName`, а email через `normalizeEmail`. Имя можно не указывать: получится «Гость». Если email не годится, брось `IllegalArgumentException` и оставь черновик доступным для исправления.
- При успехе верни готовый `Registration`. С этого момента все три метода должны бросать `IllegalStateException`.

Проверь одну историю: введи имя `"  Маша  "` → попробуй отправить без email → получи ошибку → введи `" m@b "` → отправь и получи `Registration("Маша", "m@b")` → попробуй ещё раз изменить имя: теперь это ошибка состояния.

Обсудим: в какой момент можно менять признак «отправлено» и почему не раньше?

## [8. Сканер билетов · 20 минут](tasks/Task08.kt)

У входа сканируют билет. Если код не виден, билет можно показать ещё раз. Если устройство сломалось, сотрудник должен узнать о поломке. Не превращай эти два случая в один `null`.

1. Допиши свой класс исключения `TicketCheckException`: он наследуется от `RuntimeException` и сохраняет переданные `message` и `cause`. После создания исключения `cause` должен указывать на исходный объект, а не на новую ошибку с тем же текстом.
2. Допиши `TicketInspector.inspect(reader)`. Прочитай код один раз. Убери пробелы по краям. Верни непустой код. Если сканер вернул `null` или строка пуста после обрезки, верни `null`.
3. Если `readCode()` бросил `ReaderException`, брось `TicketCheckException` с понятным сообщением и исходной причиной. Другие исключения пропускай без изменений.
4. После попытки чтения вызови `close()` ровно один раз: и при успехе, и при любом исключении. Считай, что `close()` не бросает исключений.

| Ответ сканера | Результат проверки |
|---|---|
| `"  A-17 "` | `"A-17"` |
| `null`, `""` или `"   "` | `null` |
| `ReaderException` | `TicketCheckException` с исходной причиной |
| `IllegalStateException` | То же исключение без обёртки |

Обсудим: что увидит сотрудник, если вместо обработки поломки написать `catch (e: Exception) { return null }`?

## [9. Бронь билета](tasks/Task09.kt)

Забронируйте один билет.
Объявите sealed interface BookingResult и внутри него два типа результата:
Booked(val remaining: Int) хранит остаток мест; SoldOut означает, что билетов нет.
Используйте data class для Booked и data object для SoldOut.
Напишите bookTicket(available: Int): BookingResult. На вход подают число ≥ 0.
Если до брони есть свободное место, верните Booked с остатком после брони одного билета.
Если мест изначально нет, верните SoldOut. Билет при Booked(0) достался человеку.
Примеры: bookTicket(3) → Booked(2), bookTicket(1) → Booked(0), bookTicket(0) → SoldOut.
